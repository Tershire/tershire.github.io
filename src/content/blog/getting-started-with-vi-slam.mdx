Visual-Inertial Odometry (VIO) is one of the most important building blocks in modern mobile robotics. It combines visual information from cameras with high-rate measurements from IMUs to estimate the robot's pose in real time — without GPS, without maps.

This post walks through the core components of a VIO system, explaining the theory and pointing to practical implementation choices.

## Why Visual-Inertial?

Pure visual odometry suffers in three common scenarios:

1. **Fast motion** — feature tracking fails when images blur
2. **Low texture** — when there's nothing distinctive to track
3. **Illumination changes** — cameras are sensitive to lighting

IMUs solve the fast-motion problem by providing high-frequency (200–1000 Hz) acceleration and angular rate measurements. Combined with vision, the system is robust to individual sensor failures.

> The intuition: vision gives you accurate, low-drift estimates over long periods. IMU gives you accurate short-term integration. Together, they're complementary.

## The Core Pipeline

A typical VIO system has four stages:

### 1. Feature Tracking

We detect keypoints in each camera frame (Harris corners, FAST features, or learned features) and track them across frames using optical flow. The quality of tracking determines everything downstream.

```cpp
// Detect FAST features
std::vector<cv::KeyPoint> keypoints;
cv::FAST(frame_gray, keypoints, 20, true);

// Track with KLT
std::vector<cv::Point2f> prev_pts, curr_pts;
std::vector<uchar> status;
cv::calcOpticalFlowPyrLK(prev_frame, curr_frame,
                          prev_pts, curr_pts,
                          status, cv::noArray());
```

### 2. IMU Preintegration

Rather than integrating IMU measurements one by one, we preintegrate them into a compact relative motion constraint between keyframes. This is the key insight from Forster et al. (2017).

The preintegration gives us:

- Relative rotation: $\Delta R_{ij}$
- Relative velocity: $\Delta v_{ij}$
- Relative position: $\Delta p_{ij}$

These can be reused across linearization points, making optimization much more efficient.

### 3. State Estimation

The VIO state vector typically includes:

| Variable | Description |
|----------|-------------|
| $R, p, v$ | Rotation, position, velocity |
| $b_a, b_g$ | IMU accelerometer and gyro biases |
| $\lambda_i$ | Inverse depth of each feature |

We optimize this state using either:
- **Filter-based**: Extended Kalman Filter (EKF) — fast, but linearizes everything
- **Optimization-based**: Sliding window smoother — more accurate, handles nonlinearity

For a real system, I recommend the optimization-based approach using GTSAM or Ceres.

### 4. Marginalization

To bound computation, we marginalize old keyframes out of the sliding window. This converts past states into a prior, preserving the information they contributed.

The Schur complement trick makes this efficient:

$$\mathbf{H}^* = \mathbf{H}_{rr} - \mathbf{H}_{rm}\mathbf{H}_{mm}^{-1}\mathbf{H}_{mr}$$

## Implementation Notes

A few things I learned the hard way:

**IMU noise calibration matters a lot.** Bad noise parameters destroy your filter. Use `allan_variance_ros` to characterize your IMU before deploying.

**Gravity initialization is tricky.** The first few seconds of startup need special handling to estimate the gravity direction reliably. Most papers skip this in description but it's critical in practice.

**Temporal calibration between camera and IMU** should never be ignored. Even 1 ms of temporal offset causes noticeable drift. Kalibr handles this well.
